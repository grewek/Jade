# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Vision

Jade is an Obsidian-like note-taking app, written in Rust, with these firm decisions:

- **UI framework: GPUI** (the framework built for the Zed editor) — chosen specifically for performance. No web technology (no Tauri/Electron/webview) anywhere in the app, including for the drawing canvas described below.
- **UI components: prefer `gpui-kit`** (community component library built on GPUI) over hand-rolling widgets; only build a custom component when `gpui-kit` has no equivalent.
- **Native Excalidraw-style canvas**: a planned drawing/diagramming feature equivalent to Obsidian's Excalidraw plugin, implemented natively on GPUI's own rendering primitives — not a port or embedding of Excalidraw's web (JS/SVG) implementation.
- **Storage format**: plain Markdown files on disk (Obsidian-vault-like), not a database.
- **Phasing**: core foundation (vault handling, markdown parsing, note linking/backlinks, search — the basic Obsidian feature set) must be stable before the native Excalidraw-style canvas is built. A project-management feature is planned even later, after the canvas.

**Do not add dependencies to any `Cargo.toml` without first asking the user for explicit approval** — this applies even to crates already agreed upon in principle (e.g. `gpui`, `gpui-kit`), ask again at the point of actually adding them.

## Project state

Workspace with two crates:

- `crates/core` (`jade-core`) — UI-independent library, zero external runtime dependencies (std only); `tempfile` is a dev-dependency only, for test-only temp vaults (see the `vault.rs` tests note below).
  - `note.rs`: `Note` — one loaded Markdown file (`id` = relative path without extension, `title` = file stem, raw `content`).
  - `links.rs`: `extract_wikilinks` — hand-written parser for `[[Target]]`, `[[Target|Alias]]`, `[[Target#Heading|Alias]]`.
  - `vault.rs`: `Vault` — recursively scans a root folder for `.md` files into `notes: HashMap<id, Note>`, and every directory (even empty ones) into `folders: HashSet<id>` (ids are `/`-separated relative paths, shared convention with note ids, e.g. a note inside a folder is `"Math/Algebra"`, its parent folder is `"Math"`). `backlinks()` builds a target-id → source-ids map by resolving each note's wikilinks (match by id, else case-insensitive title via a `title_index()` built once per call — *not* a linear scan per link, which used to make this effectively O(notes² × links) on vaults where most links resolve by title rather than id; see `benches/vault_operations.rs`, and the `fix(core)` commit that found and fixed it); `search()` does a naive substring match over title/content. `backlinks()` matters for input latency specifically because `jade-app` recomputes it on every keystroke (the live backlinks panel re-reads it on every `InputEvent::Change`), not just when switching notes. It reads a private `wikilinks: HashMap<id, Vec<WikiLink>>` cache instead of re-running `extract_wikilinks` on every note's content on every call — kept in sync incrementally at every mutation point (`create_note`/`update_note_content`/`rename_note`/`delete_note`/`rename_folder`/`delete_folder`), moving the cached value to a new key on rename rather than re-parsing unchanged content. `Vault::empty(root)` builds a notes/folders/cache-free vault (e.g. `jade-app`'s fallback when `Vault::open` fails) — needed because the cache field being private means external crates can no longer construct a `Vault` via struct-literal syntax. Still O(total links in the vault) per `backlinks()` call even with the cache (every call rebuilds the whole target→sources map from scratch) — a further step would be maintaining that map incrementally too (not yet done; the cache above already cut this by ~2.7x on its own, see `benches/vault_operations.rs`).
  - `Note::save()` writes `content` back to `path`. `Vault::create_note(title, parent)` creates a new `.md` file inside `parent` (vault root if `None`), dedupes titles *within that folder* by appending " 1", " 2", ... if taken, and returns its id. `Vault::create_folder(name, parent)` creates a directory the same way (dedupes by name, not title+extension). `Vault::update_note_content(id, content)` updates a note in-memory and persists it to disk. `Vault::rename_note(id, new_title)` renames the file in place (same folder, dedupes against existing titles the same way `create_note` does) and returns the new id. `Vault::delete_note(id)` removes the file and the in-memory entry. `note::relative_id(vault_root, path)` strips the extension (for notes); `note::relative_path_id(vault_root, path)` doesn't (for folders) — both are `/`-separated regardless of platform. `Vault::rename_folder(id, new_name)` moves the directory in place via a single `std::fs::rename` (which moves everything nested inside it too, in one atomic filesystem call), dedupes against sibling folder names the same way `create_folder` does, then rebuilds the moved subtree's in-memory `notes`/`folders` entries by dropping anything under the old id prefix and re-running `collect_entries` over the new path — simpler and less error-prone than hand-rewriting id prefixes for arbitrarily-nested children, and returns the new id. `Vault::delete_folder(id)` is the recursive counterpart (`std::fs::remove_dir_all` + dropping every `notes`/`folders` entry under that id prefix).
  - No Markdown rendering yet (that will need a real parser crate like `pulldown-cmark`, added only after explicit approval — see below).
  - **Tests** (`#[cfg(test)] mod tests` in `vault.rs`) use `tempfile::tempdir()` for a real-but-disposable vault directory per test, instead of a hand-rolled `std::env::temp_dir()` + PID/counter scheme. The returned `TempDir` guard is kept bound for the test's lifetime and cleans up on `Drop` — including on a mid-test panic/`assert!` failure, which the old manual `std::fs::remove_dir_all(&dir)` (only reached on the success path) didn't. Same pattern in `jade-app`'s headless UI tests (see below).
- `crates/app` (`jade-app`) — binary crate, depends on `jade-core` via path dependency and on `gpui-kit = "0.7"` (which re-exports `gpui-component` as `gpui_kit::component`).
  - `text_editor/` — Jade's own text editor, built directly on raw GPUI (`gpui-pre`/`gpui-base` primitives: `canvas()`, `window.text_system().shape_line(...)`, `window.on_mouse_event`, `EntityInputHandler`), **not** `gpui-component`'s `Textarea`/`Editor`. Exists because true Obsidian-style Live Preview (markdown markup hidden/revealed per-line based on cursor position, inside *one* continuously-editable surface, not separate rendered/editable widgets swapped in and out) isn't buildable on top of `gpui-component`'s own `Editor`/`Textarea`/`InlineToken` without forking it — and a fork means separately maintaining a divergent copy of someone else's editor indefinitely, which was explicitly rejected. Phase 1 (plain-text editing, no rendering) is done; Phase 2 (Live Preview rendering itself) has landed a first increment — see `live_preview.rs` below and the Backlog for what's still narrower than full CommonMark.
    - `buffer.rs`: `EditorBuffer` — a pure, GPUI-free `String` + `cursor`/`anchor` (selection) model, exhaustively unit-tested without any window/entity machinery (same pure-logic-first approach `markdown_blocks.rs`/`live_preview.rs` also use). Cursor movement is char-boundary-based, not grapheme-cluster-based (a deliberate simplification; `unicode-segmentation` would fix it but needs its own dependency approval). Sticky `preferred_column` makes `move_up`/`move_down` behave like a real editor (moving through a too-short line and back preserves the original column). `insert`/`delete_range` each snapshot the prior state onto an `undo_stack` first (`Snapshot { text, cursor, anchor }`), clearing `redo_stack` — "basic" linear undo, one entry per mutating call rather than a real editor's coalescing of a burst of typing into one step; a deliberate Phase 1 scope cut.
    - `live_preview.rs`: Phase 2's *inline* rendering model — pure, GPUI-free (same pure-logic-first approach as `buffer.rs`), exhaustively unit-tested. `build_display_line(line, active) -> DisplayLine` hand-scans one `\n`-free line (the same hand-written-parser style as `jade_core::links::extract_wikilinks`, not a reuse of it directly since hit-testing needs byte offsets that function doesn't carry) for headings/bold/italic/inline-code/strikethrough/wikilinks/blockquote-`>`-prefixes/list-markers, hiding their markup (`#`/`**`/`*`/`` ` ``/`~~`/`[[`/`]]`/`|target`/`>`) to zero display width and tagging the remaining visible text with an `InlineStyle`. Strikethrough (`~~x~~`) only recognizes the doubled-tilde GFM form, mirroring Strong's `**`/`__` pairing — a lone `~x~` is left as plain text, since GFM itself doesn't define single-tilde strikethrough either (that's a cmark-gfm extension option GitHub doesn't enable). List markers are the one exception to "hidden means gone": their raw `-`/`1.` is *replaced* with a bullet (`•`) or canonical `N. `, not left blank — `DisplaySegment::is_replaced()`, orthogonal to `is_hidden()` (a replaced segment paints real, non-empty text, just not a verbatim slice of `raw`). `DisplayLine` carries both the resulting `display_text` and a `segments: Vec<DisplaySegment>` raw↔display byte mapping (`display_offset_for_raw`/`raw_offset_for_display`) — needed because `element.rs`/`input_handler.rs` now shape and hit-test the *display* text, not the raw buffer text, once markup is hidden or replaced; both offset-mapping functions treat hidden and replaced segments alike (collapse any interior raw/display offset to the segment's boundary), since neither has a byte-for-byte correspondence to interpolate into. `active` (the line containing the cursor) always renders raw/unstyled, so an edit always sees the literal source — a deliberate v1 simplification; a "real" Live Preview editor keeps formatting visible while editing and hides only the delimiters. Emphasis matching is also simplified (`**x**`/`__x__` is bold, a lone `*x*`/`_x_` is italic) rather than CommonMark's full flanking-delimiter-run algorithm. A blockquote or list item's content gets one further look for a *compounding* construct via `compound_inner` — a heading (checked unconditionally; a heading never itself compounds further, since it swallows the rest of the line as inline content), or whichever of blockquote/list the outer one wasn't — so `> # Heading` hides both the `> ` and the `# ` (not just the former), `- # Heading`/`- > quoted`/`> - item` likewise. Only one level deep, and never list-in-list on the same line (`- - x` leaves the second `-` as plain text — list nesting is signaled by indentation, not by repeating the marker, same as real CommonMark). Also exposes `hidden_line(line)` for `element.rs` to use on a fence delimiter line or (see below) a thematic break. `element.rs`'s `strikethrough_for_style` maps `InlineStyle::Strikethrough` to a `TextRun.strikethrough: Some(StrikethroughStyle)` (GPUI's native strikethrough paint, not a hand-drawn quad) — same color as the run's own text, `1px` thick, not yet pulled from the theme (see `MUTED_COLOR` etc. below). `LineIndent` (`None`/`Blockquote(depth)`/`List(depth)`, with a `level()` returning the depth, `0` for `None`) is a second, orthogonal piece of per-line data alongside `segments`/`display_text`: a *structural* fact about the line, not a Live Preview hiding choice, so (unlike every `InlineStyle`) it's computed and set even on the active line via a standalone `line_indent(line)` helper that `build_display_line` calls unconditionally before its early-return branches — a quoted or list line is still structurally one while you're actively typing it, even though its `>`/`-` renders raw rather than hidden/replaced while active. `build_display_line` alone always resolves a list line to depth `1` (via `indented_list_marker`, a leading-whitespace-tolerant `list_marker` — it hides the whitespace too, but one line alone can't know a marker's *true* nesting depth). **A later spec-gap-fill pass added**: backslash escapes (`ConstructKind::Escape`, matched in `find_construct` whenever a `\` is immediately followed by `u8::is_ascii_punctuation()` — a one-shot match with no closer to search for, so `\*` is caught *before* the following `*` could ever register as an emphasis opener, no extra ordering logic needed); HTML entity references (`ConstructKind::Entity`/`parse_entity` — numeric `&#NNN;`/`&#xHHH;` decode any valid codepoint, named references are looked up in a `NAMED_ENTITIES` common subset, not HTML5's full ~2000-entry table, a deliberate v1 scope cut); a thematic break (`is_thematic_break` — `---`/`***`/`___`, optionally space-separated, at least 3 of the same character and nothing else on the line — resolved per-line like every other inline detector here, unlike fences/tables, and rendered by `element.rs` as `hidden_line` plus a real vector rule painted by `paint_lines`, the same "quad over a blank gap" technique as a table's own grid lines); inline links (`[text](url)`, `InlineStyle::Link`/`parse_link` — a leading `!` suppresses the match entirely, since `![alt](url)` is an image and images are explicitly deferred, no bitmap-paint pipeline exists in this editor); autolinks, both the bracketed CommonMark form (`<https://x>`/`<a@b.com>`, `ConstructKind::AutolinkBracket`/`parse_autolink_bracket` — requires `://`/`mailto:`/`@` inside the brackets, so ordinary `<div>`-style raw HTML, also explicitly declined, still falls through as plain text) and the bare GFM extended form (`https://x` with no delimiters at all, `ConstructKind::BareUrl`, matched directly in `find_construct` on a literal `http://`/`https://` prefix — lowercase scheme only, a deliberate simplification); and GFM task-list checkboxes (`push_list_marker`/`task_checkbox_prefix`, folded into the existing list-marker handling in both `build_display_line`'s own branch and `compound_inner`'s — render-only, no click-to-toggle yet, same deferred-interactivity category as WYSIWYG table editing below). An **unordered** marker's bullet and its checkbox collapse into *one* glyph (`"- [ ] x"` → `"☐ x"`, not `"• ☐ x"`, matching Obsidian/GitHub's own task-list rendering), but an **ordered** marker keeps its number and gets the checkbox appended after it (`"1. [ ] x"` → `"1. ☐ x"`) — the number still carries meaning a checkbox alone doesn't. `find_closing` became escape-aware as the shared foundation underneath all of this (loops past any delimiter match immediately preceded by `\`, so e.g. `*italic \* still italic*` doesn't close early at the escaped asterisk) — a no-op for every pre-existing caller's own tests, and reused by the new Link/autolink closing searches too; the escape itself isn't recursively unescaped *inside* an emphasis/strong/strikethrough span's content though (that content is still one opaque visible span, not re-scanned — same simplification that already keeps emphasis from compounding with other emphasis). Setext headings, 4-space indented code blocks, link reference definitions (`[text][ref]`/`[foo]: url`), and raw inline/block HTML are **explicitly declined, not just deferred** — see the Backlog for why.
  - **Nested-list depth and lazy continuation need cross-line state**, unlike everything else `live_preview.rs` detects — `classify_block_context(source) -> Vec<LineContext>` is this module's own whole-document pass resolving both, mirroring `block_preview::classify_lines`'s fence-tracking state machine but tracking open-list indentation columns and open-block state instead of fence delimiters. For each line it's one of: `LineContext::Plain` (nothing to override — not part of any list/quote, or it has its own unambiguous prefix `build_display_line` already resolves correctly), `ListMarkerLine(depth)` (an indented marker's real nesting depth, computed by popping/reusing/pushing an indentation-column stack as each successive marker line is seen — a deeper indentation opens a new level, the *same* column reuses the current level as a sibling item, anything shallower pops back to an ancestor), or `LazyContinuation(LineIndent)` (a line with no marker of its own, still styled as that block's content — `Blockquote(depth)` color, or `Plain` for a list item's continuation — because CommonMark treats it as continuing the open paragraph). A blank line or a heading always closes whatever was open (both unambiguously interrupt a paragraph in CommonMark); a fresh blockquote/list line replaces whichever was previously open outright, rather than nesting the two together (compounding a blockquote and list only happens within `compound_inner`'s one-line, one-level check, not across lines). `build_display_line_in_context(line, active, ctx)` is what actually applies a `LineContext`: for `ListMarkerLine`, it's `build_display_line` with its `LineIndent` overridden to the real depth; for `LazyContinuation`, since there's no prefix of its own to hide, the *entire* line (unless `active`) is inline-scanned with the enclosing block's style. `element.rs`'s `render_editor` computes `classify_block_context` once per paint (alongside `classify_lines`) and feeds `shape_display_line` the matching `LineContext` per line, which calls `build_display_line_in_context` instead of `build_display_line` for `LineRole::Plain`. Lazy continuation here is deliberately more lenient than real CommonMark: a continuation line stays part of the open list *regardless of its own indentation* (mirroring blockquote's own already-indentation-free lazy continuation), not CommonMark's stricter per-item content-column alignment — simpler to reason about and test, at the cost of occasionally keeping an unindented line "in" a list a strict CommonMark parser would kick out.
  - `element.rs`'s `indent_px(level) -> Pixels` (`pub(super)`, also used by `input_handler.rs`) converts a `LineIndent::level()` into the actual pixel shift, via a flat `INDENT_UNIT` constant (same "not yet pulled from the theme" status as `SELECTION_HIGHLIGHT`/the color constants) — applied identically in three places so painted position and hit-testing/IME math never disagree: `paint_lines` shifts each line's `line_origin.x` by it (so text, the selection highlight, and the cursor caret all move together), `offset_for_position` subtracts it from a click's `relative_x` before hit-testing (clamped to `0`, so a click anywhere in the indent gutter lands at the start of the line's actual content, same landing spot a click on a list's bullet glyph already had), and `input_handler.rs`'s `bounds_for_range` adds it to the IME candidate window's x. A blockquote additionally gets a left "quote bar" per nesting level — `paint_lines` paints one `QUOTE_BAR_WIDTH`-wide `MUTED_COLOR` quad per level at `indent_px(level) + QUOTE_BAR_INSET`, spanning the full line height; a list item gets the indent shift but no bar, matching Obsidian's own list-vs-quote visual distinction. `shape_display_line` force-resets `LineIndent` to `None` for `LineRole::FenceContent` after calling `build_display_line` — fenced code content is never Markdown (see `block_preview.rs`'s note), so a code sample that happens to start with `>` or `- ` (e.g. a shown diff or YAML list) must not be mistaken for a real blockquote/list line and indented as one.
    - `block_preview.rs`: fenced code (`` ``` ``/`~~~`), the only thing that can't be classified one line at a time (whether a line sits inside an open fence depends on earlier lines). `LineRole` (`Plain`/`FenceDelimiter`/`FenceContent`) + `classify_lines(source) -> Vec<LineRole>`, a hand-written single sequential pass tracking fence open/close state — not `markdown::to_mdast` (see `markdown_blocks.rs`'s note below for why not), since fence-boundary detection is as mechanical as `live_preview.rs`'s own detectors. Pure, GPUI-free, exhaustively unit-tested (unclosed fence at EOF, multiple fences, too-short closing run per CommonMark, `` ``` ``/`~~~` both recognized). Computed once per paint (`render_editor`) since it needs the whole document, unlike every `live_preview.rs` detector.
  - `table_preview.rs`: tables — the *other* block-level construct, independent of `block_preview.rs`'s fence tracking and `live_preview.rs`'s `classify_block_context` (neither of those three knows about either of the others). `scan_row(line) -> Row` splits a `|`-delimited row into `Cell`s (each with its raw byte range *and* trimmed, `\|`-unescaped text) — tolerant of an optional leading/trailing pipe, per GFM. `classify_tables(source) -> (Vec<Option<usize>>, Vec<Table>)` is this module's own whole-document sequential pass (same kind block_preview/live_preview already use): a pipe-row immediately followed by a valid delimiter row (`delimiter_align` parses each `---`/`:--`/`--:`/`:-:` cell; GFM requires its cell count to exactly match the header's) starts a `Table`, which continues through every following pipe-row until a blank line, a non-pipe line, or EOF. A `Table` carries `start_line`/`end_line`, its overall `byte_range` (see `element.rs`'s whole-table-active policy below), and resolved `columns: Vec<Column>` (`width` = the widest cell's *character* count across the header and every body row — not just the delimiter row — `align` from the delimiter). A body row with fewer/more cells than the header is padded/truncated when rendered, not rejected (unlike the delimiter row, which must match exactly). `pad`/`pad_amounts` right-pad/left-pad/center a cell's text to its column's width — `pad_amounts` exposed separately so `live_preview.rs`'s renderer can interleave real (byte-mapped) content between the two pad amounts instead of building one opaque string.
    - **Rendering a table as an actually-*aligned grid*** (not just markup hidden/replaced in place, unlike every other construct) is tractable without any pixel measurement because this editor's font is always monospace (`element.rs`'s `render_editor` overrides `font.family` for the whole editor, not just code) — a column's width in *characters* lines up pixel-for-pixel across every row, so alignment is purely a property of the string `live_preview.rs`'s `build_table_row` constructs. `build_table_row` pads each cell to its column's width and separates cells with *blank* space (not a box-drawing glyph — see the next bullet for why); `shape_display_line` renders a delimiter row as `hidden_line(line)` (no cell content of its own to show at all). The tricky part was keeping cell text a genuine *click target*: a naive one-`push_replaced`-segment-per-blank-gap-and-cell (padded display text, raw = the cell's own span) makes `raw_offset_for_display` skip it entirely (same collapse-to-next-segment behavior a list marker's bullet already relies on, since that function treats every `is_replaced()` segment as unclickable) — with *every* segment in a row replaced that way, a click anywhere in the row fell through all the way to the line's end. Fixed by `push_cell_content` splitting each cell into its original (trimmed-away) whitespace — replaced with the column's real alignment padding — plus the trimmed text itself pushed via `push_visible` (a genuine byte-for-byte mapping) whenever it contains no backslash (i.e. no `\|` for `scan_row` to have unescaped); the rarer escaped-pipe case falls back to one collapsing `push_replaced` segment for that cell, a known (not regressive) imprecision. **Whole-table-active policy**: unlike every other construct's single "active line," a table's row/column alignment can't be resolved from one line in isolation, so there's no sensible way to keep the rest of the grid rendered while one row inside it goes raw — `element.rs`'s `is_table_active` (checks the cursor against the whole `Table::byte_range`, `focused`-gated like `is_active_line`) makes the cursor being *anywhere* in the table render the *entire* table raw via `build_display_line(line, true)`, same as flipping any other construct's own active-line switch. `table_line_kind` resolves a line's `TableLineKind` (`None`/`Delimiter`/`Row`) from `classify_tables`' per-line lookup, threaded through `shape_display_line` (now also taking `table_kind`/`table_active`) alongside `line_roles`/`block_contexts`, computed once per paint in `render_editor` the same way. A table nested inside a blockquote/list (`> | a | b |`) isn't recognized, and a table-like pipe sequence inside a fenced code block is never mistaken for a real one (nothing ever looks `table_for_line` up for a `LineRole::FenceContent`/`FenceDelimiter` line) — both deliberately out of scope, consistent with every other compounding limit already in this editor.
    - **A table's grid lines (outer box, column dividers, header/body divider) are painted as real vector quads, not box-drawing glyphs** (`┌`/`│`/`┼`/etc.) — a monospace font's glyphs don't reliably abut pixel-for-pixel across separately-shaped/painted lines or at junctions, which read as visible seams/gaps between them (an earlier version of this feature tried the glyph approach; replaced after it visibly didn't look like a clean closed box). `build_table_row_line`/`build_table_row_wrapped_line` leave a *blank* (space-filled, `InlineStyle::Plain`) gap everywhere a border glyph used to go — same character widths as before (`table_preview::cap_column_widths`'s own border-overhead accounting is unchanged), just nothing drawn there as text. `element.rs`'s `paint_lines` paints the actual lines directly over those gaps: `table_preview::column_divider_char_offsets(widths)` gives the *character* offsets (left outer edge, one between each pair of columns, right outer edge) that `build_table_row_line` left blank, matching its exact layout without needing to lay out any text itself; `mono_char_width` (shared with `table_row_char_budget`, split out of it) converts one such offset to a pixel x. `paint_lines` accumulates a `TablePaint { top, divider_y, column_x }` while walking a table's own lines top to bottom — `column_x` and `top` resolved on the header row (`Table::is_first_row`), `divider_y` (the header/body rule's y, at the vertical center of the delimiter row's own line-height-tall slot) on the delimiter row, and the whole thing painted (`paint_table_grid_lines`, one quad per vertical divider plus top/bottom/divider horizontal quads) and dropped once `Table::is_last_line` is reached — `is_last_line` compares against `end_line - 1` since `end_line` itself is exclusive, and is checked on whichever of `TableLineKind::Row`/`Delimiter` this table's actual last line turns out to be (a table with no body rows at all has its delimiter row double as both the divider *and* the last line, in that order, within the same loop iteration). Skipped entirely while a table is rendering raw (`table_active`) — no grid is painted then, matching every other construct's "border disappears while active" behavior. `InlineStyle::TableBorder` was removed outright once nothing needed a distinct border-glyph color any more.
    - **A table too wide for the pane never overflows it**, even though a table row/rule is otherwise exempt from the GPUI-level soft-wrapping every other line gets (see "Soft line-wrapping" below) — overflowing sideways past the editor's own width would be exactly the bug that feature exists to fix for every other construct. `table_preview::cap_column_widths(columns, max_total_chars)` first shrinks every column's natural width down to fit a character budget (proportionally to how much each column could shrink, i.e. a wide column gives up more than a narrow one; never below `MIN_COLUMN_WIDTH`, after which it's just clamped flat at that floor once the budget is too tight to proportion at all), then any cell whose text still doesn't fit its now-capped column gets word-wrapped *within that cell* by `table_preview::wrap_cell_text` (greedy word-fill, hard-breaking a single word too long for an empty line on its own) rather than left overflowing. `table_preview::resolve_widths(columns, max_total_chars)` is the one place both `build_table_row` and `paint_lines`'s own grid-line geometry resolve this (`Some` → capped, `None` → natural), so they can't disagree about where a column's blank gap actually is. `element.rs`'s `table_row_char_budget` converts the editor's actual available pixel width into that character budget via `mono_char_width` — `None` (meaning "don't cap or wrap, use natural widths") if the available width or that measured advance is non-positive. `build_table_row` takes this optional budget: when every cell still fits, nothing changes (still exactly one returned line, byte-exact click mapping via `push_cell_content`); when a cell needs wrapping, `build_table_row` returns *multiple* `DisplayLine`s for that one raw row (one per wrapped sub-row, via `build_table_row_wrapped_line`) — the one case (besides GPUI's own soft-wrap) where `shape_display_line` can return more than one `(WrappedLine, DisplayLine)` entry for a single raw line, which is why every caller already iterates its result rather than assuming exactly one; `paint_lines`'s own grid-painting logic doesn't care, since it only ever reads a line's *total* (already-summed) height, not its entry count. A wrapped row's cells fall back to one collapsing `push_replaced` segment per cell (clicks land at that cell's raw start, not byte-exact within it) since no single sub-row is the cell's whole verbatim text any more — a known, deliberate v1 imprecision, same category as the escaped-pipe fallback above.
  - `callout.rs`: Obsidian-style callouts (`> [!info]` etc.) — the *other* construct besides `table_preview.rs` needing cross-line state, for a narrower reason: telling a callout's *header* line apart from a body line that also starts with `>` requires knowing whether the blockquote block just opened on this line or is continuing from above, which `live_preview::classify_block_context`'s own `Open::Blockquote` state never needed (every `>`-prefixed line is already self-sufficient for plain blockquote rendering). `classify_callouts(source) -> (Vec<Option<usize>>, Vec<Callout>)` is this module's own sequential pass, same shape as `classify_tables`, tracking `block_open` (was the previous line part of an open blockquote block at all) and `current` (which `Callout`, if any, that open block is). A line opens one when it's a *fresh* depth-1 blockquote line (its own tiny `blockquote_depth` scan, deliberately not reusing `live_preview`'s private one — same "each scanner is self-contained" precedent `block_preview.rs`/`table_preview.rs` already set) whose content matches `callout_header_prefix` (`[!type]` + optional `+`/`-` fold marker + optional ` title`); `resolve_callout_type` maps the raw, case-insensitive type name to one of 13 `CalloutType` groups via Obsidian's own alias list (`hint`/`important` → `Tip`, `done`/`check` → `Success`, etc.), defaulting to `Note` for anything unrecognized — matching real Obsidian, which still renders an unknown type as a callout rather than rejecting it. **Top-level only**: a `>>`-nested line is never checked as a potential header (callout-in-callout and callout-in-list-item are both out of scope, consistent with every other one-level compounding cap in this editor) — it stays part of the enclosing callout's body, rendered as plain nested blockquote content. `Callout` deliberately only carries `kind`/`start_line`/`end_line`, not the parsed header itself — unlike a table's column widths, a header is resolvable from its own single line alone, so `live_preview::build_callout_header_line` re-parses it fresh via `callout_header_prefix` rather than this struct caching it (same "store only what's genuinely cross-line" reasoning `Table` already follows by not caching `Row`/`Cell`). `callout_icon(kind) -> &'static str` (one Unicode glyph per group, from the same range the already-shipped `•`/`☐`/`☑` glyphs come from) lives here rather than in `element.rs` — unlike color (`Hsla`, an actual GPUI type), a glyph is just a `&str` with no GPUI dependency, so it stays with the rest of this module's pure data. Render-only, not interactive: the fold marker is parsed and hidden so it doesn't leak into the title, but collapsing is deliberately not implemented yet — every callout always renders fully expanded regardless of `+`/`-` (or no marker at all); see the Backlog.
    - `live_preview::build_callout_header_line(line, active)` is what actually renders a header line once `classify_callouts` has identified one — raw/unstyled if `active`, same as every other construct; otherwise hides `> [!type]+/-` (and one separating space) entirely, then either inline-scans a custom title (so it can itself contain `**bold**`/links/etc., styled the new `InlineStyle::CalloutTitle`) or, if there isn't one, shows the raw type name as typed — capitalized, matching Obsidian's own display of what you actually wrote rather than the resolved alias group's name — as synthetic replacement text in the same style. Either way, `callout_icon`'s glyph is prepended directly into the rendered text (a zero-width-raw `push_replaced` insertion when there's a title, folded into the single synthetic-text replacement when there isn't) rather than painted separately in `element.rs` — simpler than positioning a floating icon glyph, and sidesteps needing any new paint call for it at all. A callout's *body* lines need no `live_preview.rs` changes at all — they're still ordinary blockquote content via the existing `build_display_line_in_context`; only their *paint color* differs, an `element.rs`-only concern (next bullet), keeping this module's GPUI-free boundary intact.

  - **Soft line-wrapping** (fixing a real overflow bug — a line too wide for the pane used to be simply unreadable, clipped/overflowing past the editor's own width with no horizontal scroll either) — `shape_display_line` now calls `WindowTextSystem::shape_text(text, font_size, &runs, wrap_width, None)` instead of `shape_line`, returning a `WrappedLine` (not `ShapedLine`) that can paint/hit-test across more than one visual row for a single raw line. `wrap_width_for` picks the width: `available_width - indent_px(level)` normally, `None` (never wrap) for a table row/rule specifically (`table_kind`, unless `table_active`) — wrapping would break a table's column alignment, a correctness issue, not just a style call the way wrapping everything else (including fenced code content) is. A too-wide table isn't simply left to overflow, though — see `table_preview.rs`'s own "too wide for the pane" bullet above for its separate column-capping/cell-wrapping mechanism. This is a real architecture shift, not just a parameter: every place that used to assume "one raw line = exactly one `line_height`-tall row" needed to stop doing that —
    - `paint_lines`/`offset_for_position` (in `element.rs`) and `bounds_for_range` (in `input_handler.rs`) all now track a running accumulated Y offset across lines (each line's own height is `WrappedLineLayout::size(line_height).height`, a multiple of `line_height` once it wraps) instead of multiplying `line_height * i`. `offset_for_position`'s click→byte math and `bounds_for_range`'s IME-bounds math both switched from `ShapedLine`'s 1D `closest_index_for_x`/`x_for_index` to `WrappedLineLayout`'s 2D `closest_index_for_position`/`position_for_index` (a full `Point`, since which wrapped *row* matters now too, not just x). `paint_lines`'s selection highlight is the one genuinely more complex case: a selection spanning more than one wrapped row *within the same raw line* now paints one rect per affected row (first row: selection-start to the row's own right edge; last row: left edge to selection-end; any rows between: full width) rather than the single rect that sufficed when every line was exactly one row.
    - `render_editor`'s outer `div` needs its total height *before* constructing the element tree (i.e. before the `canvas` paint closure that normally does per-line shaping even gets to run) — a real problem once that height depends on wrapping, which depends on a width this function doesn't actually know yet at that point (layout hasn't happened). `measure_document` (new) solves this by shaping every line once up front to get `(total_height, cursor_top, cursor_height)` (the latter two feed `autoscroll_to_cursor`, which switched from `(line_height, cursor_line_index)` to these two already-computed pixel values directly), using `editor.scroll_handle.bounds().size.width` as the available-width estimate — the same "last completed layout" value `autoscroll_to_cursor` already relied on for the *viewport's* bounds, reused here for the *editor's own* width. Falls back to `Pixels::MAX` (effectively "assume no wrap" for this one estimate) when that's zero — before a tracked ancestor (`main.rs`'s `note-editor-pane` div, via `.track_scroll(...)`) has ever been laid out for this specific `Editor` — confirmed empirically (`main.rs`'s own `a_line_too_wide_for_the_pane_wraps_instead_of_overflowing` test) to already resolve correctly on the *first* render after opening a note in the real app, not needing a stale extra frame to catch up. A bare `Editor` with no such tracked ancestor (`text_editor::element`'s own test harness) always hits that `Pixels::MAX` fallback — which is why wrapping-aware *sizing* specifically can only be tested through the full `main.rs`/`JadeApp` harness; `shape_display_line`'s own wrapping *mechanism* is still directly testable in isolation by just passing it an explicit narrow width.

This protocol speaks UTF-16 offsets (macOS/Windows text services are UTF-16-native) while `EditorBuffer` is UTF-8 internally, hence the `utf16_to_utf8`/`utf8_to_utf16` conversion helpers at the boundary (tested against surrogate-pair codepoints above U+FFFF). `character_index_for_point` returns `None` (not passed this element's bounds, unlike `bounds_for_range` — only affects secondary OS text-service affordances, not typing/IME). `bounds_for_range` (IME candidate-window positioning) reuses `element.rs`'s `is_active_line`/`shape_display_line`, recomputing `block_preview::classify_lines` locally the same way it already recomputes everything else per call, so it agrees with whatever was actually painted for that line.

    - `scroll_handle: ScrollHandle` (`Editor::scroll_handle()`) — owned per-`Editor` (not by `JadeApp`) so it resets naturally per opened note. `main.rs`'s `note-editor-pane` div calls `.track_scroll(editor.read(cx).scroll_handle())` so the handle can actually move that container's scroll offset; `element.rs`'s `render_editor` reads/writes the *same* handle (shared via `ScrollHandle`'s `Rc<RefCell<_>>`) every paint via `autoscroll_to_cursor`, scrolling the cursor's line into view whenever it isn't (only while focused) — comparing the editor's own (already scroll-shifted) on-screen bounds against the tracked container's fixed viewport bounds, since a plain `div().overflow_y_scroll()` has no built-in "scroll this into view" behavior of its own (that's `request_autoscroll`/`take_autoscroll`, meant for an element like `List` to implement itself — a bare `div` doesn't, so `autoscroll_to_cursor` computes and applies the needed offset directly instead). **Gated by `last_autoscrolled_cursor: Rc<Cell<Option<usize>>>`**, another field on `Editor` — `render_editor` rebuilds its whole element tree (fresh `canvas` closures included) on *every* actual screen repaint, not only ones triggered by an actual cursor move: a plain mouse-wheel scroll alone forces one too. Without this gate, `autoscroll_to_cursor` ran unconditionally on every such repaint and snapped the view straight back to the (unchanged) cursor's line the instant a manual scroll carried it out of the viewport, making it impossible to scroll away from the cursor at all (bug: scrolling "blocks" after a few lines). The paint closure now only calls `autoscroll_to_cursor` (and updates this field) when the *current* cursor offset differs from the one it last recorded — an `Rc<Cell<_>>`, not a plain field, for the same reason `scroll_handle` itself is `Rc`-backed: `render_editor` clones it out of `&Editor` synchronously (a direct field read, always safe) and moves the clone into the `'static` paint closure, which mutates it directly, rather than calling `editor_entity.read/update(cx)` from inside paint (not proven safe there, unlike inside the mouse-event closures nested *further* inside paint, which run later during event dispatch). Regression test: `main.rs`'s `scrolling_away_from_the_cursor_does_not_get_snapped_back`.

  - **Rename/delete** are deliberately *not* exposed as sidebar buttons — only via right-click context menu (`gpui_kit::component::menu::ContextMenuExt::context_menu`, items built with `PopupMenuItem`) or via hotkey (`F2` = rename, `Backspace` = delete), matching Obsidian's file-list UX. Both paths call the same `JadeApp::open_rename_dialog`/`open_delete_dialog` associated functions (take the target note's id/title/an `Entity<JadeApp>` + `window`/`cx` explicitly — not `&self` — since context-menu item callbacks only ever get `(&ClickEvent, &mut Window, &mut App)`, no `Context<JadeApp>`).
    - **Folders** have the same Rename/Delete, but *only* via their context menu (appended after "New note"/"New folder", so existing tests' 0-based item indices for those two stay valid) — no hotkey, since there's no "selected folder" concept to scope a hotkey to (only notes are ever "selected"). `JadeApp::open_rename_folder_dialog`/`open_delete_folder_dialog` mirror the note versions' dialog/`on_ok` structure exactly, with their own element ids (`"rename-folder-input"`, `"confirm-rename-folder"`, `"cancel-rename-folder"`) distinct from the note-rename dialog's, so a test could in principle target either one unambiguously (only one dialog is ever open at a time in practice). `JadeApp::rename_folder`/`delete_folder` both call `flush_editor` first (same reasoning as `open_note`'s own flush — the operation can move or delete the very id that flush would otherwise target, so it has to happen first) before calling into `Vault`, then reconcile `JadeApp`'s own state against the folder's old id prefix: `rename_folder` remaps `collapsed_folders`'s entry for the renamed folder itself (not nested descendants — resetting a deeply-nested collapsed subfolder's state on an ancestor rename is an acceptable minor cosmetic surprise, not worth the extra bookkeeping) and, if the open note was nested anywhere under the renamed folder, recomputes its new id and reloads it via `open_note`; `delete_folder` clears any `collapsed_folders` entries under the deleted prefix (so a future folder of the same name doesn't inherit a stale collapsed flag) and clears `self.editor` if the open note was nested under the deleted folder.
    - The hotkeys are scoped to a `"NoteList"` key context (`gpui_kit::actions!(jade, [RenameNote, DeleteNote])`, bound via `cx.bind_keys([KeyBinding::new("f2", RenameNote, Some("NoteList")), ...])`), active only while the sidebar's `FocusHandle` (`JadeApp::sidebar_focus`) is focused — set by `.track_focus(&self.sidebar_focus).key_context("NoteList")` on the sidebar container, and re-focused on every note click (and on "New note"/"New folder"). This is required so `Backspace` deletes the selected note only when the list has focus, not every backspace keystroke while editing a note's text in the editor.
    - Rename and "New folder" both open a plain `Dialog` (`gpui_kit::component::dialog::Dialog` via `WindowExt::open_dialog`) with a single-line `Input`/`InputState` and a custom `DialogFooter` (a plain `Dialog` renders no default buttons — only `AlertDialog` does). **Both also set `.on_ok(...)` with the same commit logic as the footer's confirm button** — `on_ok` is what the dialog's built-in Enter-key handling actually dispatches to, independent of whatever footer buttons are rendered; without it, Enter silently does nothing and only clicking the button works. Rename's confirm calls `Vault::rename_note` and, if the renamed note was open, reloads it via `open_note` (safe because every edit already autosaves, so there's nothing unsaved to lose). Delete opens an `AlertDialog` (`WindowExt::open_alert_dialog`, `.confirm().ok_variant(ButtonVariant::Danger)`) since it's destructive — its default footer already wires `on_ok` to both the OK button and Enter, so it didn't need this fix; its default OK/Cancel buttons have the fixed ids `"ok"`/`"cancel"`.
    - Tree-row indentation uses `.ml(px(depth * N))` (margin), not `.pl(...)` (padding) — padding only insets a box's *content* and never moves the box itself, so it has zero effect on sibling rows' horizontal alignment in a vertical flex list; margin is what actually shifts a row's position. Learned by writing a test that asserted on `ElementSnapshot::bounds().origin.x` and watching it come back identical at every depth despite the (wrong) `.pl(...)` call.
    - To update a *different* entity (not the one currently mid-update via an action handler) from inside a dialog button's `on_click`/`on_ok` callback: don't reach for `Entity::update_in` (it needs a `VisualContext`, which a plain `&mut Window` does not implement here) — just capture `window: &mut Window` from the callback's own parameters and call `entity.update(cx, |state, cx| state.some_method(window, cx))`, letting the inner closure borrow the outer `window` directly. This is the same pattern `gpui_component::root::WindowState::update` uses internally.
  - **Headless UI tests** (`#[cfg(test)] mod tests` at the bottom of `main.rs`, run via `cargo test -p jade-app`): use `gpui-kit`'s built-in `test-support` feature (enabled only under `[dev-dependencies]` in `crates/app/Cargo.toml` — release/`cargo run` are unaffected) to render the real `JadeApp` in an off-screen window and drive it with real GPUI hit-testing (`gpui_kit::test::TestWindowExt::click`/`press`/`input`/`right_click` by element id) — no `ydotool`/display/compositor needed, safe to run unattended; **prefer this harness over `ydotool`-driven manual testing** for any `jade-app` UI change, since it carries no risk of input landing on the user's own live desktop session. Any interactive `div` that a test needs to `click(...)` must carry `.test_support()` (a zero-cost no-op outside test builds) in addition to `.id(...)`, or the click silently can't find it. Opening an overlay (context menu, dialog) is asynchronous even in tests — a test must call `cx.run_until_parked()` between triggering the overlay (right-click, hotkey) and interacting with it (e.g. `window.within("popup-menu").within("items").click(<index>, cx)` for a context-menu item by its 0-based position), split across separate `cx.update_window(...)` calls; doing it all inside one `update_window` closure silently finds nothing. Inside the test module, import gpui-kit items explicitly rather than `use gpui_kit::*`/`use super::*` glob — with `test-support` on, that glob also re-exports GPUI's `test` attribute macro, which shadows plain `#[test]` and makes `#[gpui_kit::test]`'s own expansion recurse infinitely. Each test's vault lives in a `tempfile::tempdir()` `TempDir` guard (not a hand-rolled temp-dir scheme), same rationale as `jade-core`'s tests. **Must be run with `--test-threads=1`** (`cargo test -p jade-app -- --test-threads=1`) — running the default parallel test harness is non-deterministic: any test that opens an overlay (dialog/context menu) and waits on it via `cx.run_until_parked()` can intermittently fail as if the action/hotkey never dispatched, or as if a click had no effect, even though `window.click`'s own dispatch (`dispatch_event` + `render_frame`) is fully synchronous with no async step in Jade's or `gpui-component`'s dialog code. Confirmed via controlled A/B testing under added CPU load (12 busy-loop processes pinning all 16 cores): single-threaded (`--test-threads=1`) stayed at 0 failures across 35 runs both with and without the extra load, while the default parallel harness went from an occasional failure at idle to roughly 80% of runs having at least one failure under load — and the failures weren't confined to one test, implicating a genuine concurrency bug in the vendored `gpui`/`gpui-base`/`gpui-component`/`gpui-kit` test-support stack (likely in its thread-local element-observation registry or test executor's "parked" detection, not yet pinned down further) rather than anything in Jade's own code or the `tempfile` migration. Re-check this note if a future `gpui-kit` upgrade might have fixed the underlying race — don't just re-add parallel test execution without re-verifying under load first.
  - **Fonts**: `crates/app/assets/fonts/` bundles IBM Plex Sans (UI, Regular/Italic) and IBM Plex Mono (editor, Regular/Italic/Bold/BoldItalic) — the same family Zed itself uses — under the SIL Open Font License 1.1 (`LICENSE.txt` next to each family's `.ttf` files; the OFL explicitly permits bundling/embedding fonts with an application, provided the license travels with them and the reserved name "Plex" isn't reused for a derivative). `main.rs`'s `install_fonts(cx)` (called from `main()` right after `gpui_kit::init(cx)`) embeds the `.ttf` files via `include_bytes!` and registers them with `cx.text_system().add_fonts(...)`, then sets `gpui_kit::component::Theme::global_mut(cx).font_family`/`.mono_font_family` to `"IBM Plex Sans"`/`"IBM Plex Mono"` — the latter is what `gpui-component`'s own `Textarea`/`Editor` read for their font per its `input/editor.rs`, and (since Live Preview landed) what `text_editor::element`'s own `render_editor` reads too, for the same reason. Fonts must be embedded (not just installed system-wide) since IBM Plex isn't a font users are expected to already have.

**Requires nightly Rust** — `gpui-pre` (pulled in transitively by `gpui-kit`) uses the unstable `std::hint::cold_path`, which only compiles on nightly. Pinned via `rust-toolchain.toml` (`channel = "nightly"`), so plain `cargo build`/`run`/`test` pick up nightly automatically; no `+nightly` needed.

Edition 2024, built with Rust 1.93 / Cargo 1.93 (stable toolchain version; actual builds use the pinned nightly).

## Backlog

Deliberately deferred follow-ups — don't pick these up without checking in first, they're parked on purpose:

- **`Vault::backlinks()` still rebuilds its whole target→sources map from scratch on every call** (O(total links in the vault), not O(1)), even after the `title_index`/wikilink-cache fixes. A further step would be maintaining that map incrementally (diff a note's old vs. new links on edit; also needs to account for `resolve()`'s targets shifting when *other* notes are renamed). Not done because even the worst-case measured cost (16.9ms on a 200-note × 20k-word synthetic vault) is already comfortably under the ~100ms human-perceptible-lag threshold — real complexity for a return past the point of mattering, for now.
- **Live Preview Phase 2, eight increments landed**: inline constructs (`text_editor::live_preview` — headings/bold/italic/inline-code/strikethrough/wikilinks/blockquotes/list-markers), fenced code (`text_editor::block_preview`), visual indentation + a blockquote quote-bar (`LineIndent`, `element.rs`'s `indent_px`/`paint_lines`), one-level-deep compounding of a blockquote/list with a heading or each other (`compound_inner`), indented nested lists + lazy continuation lines (`live_preview::classify_block_context`/`LineContext`/`build_display_line_in_context`), tables rendered as an actually-aligned, fully-boxed grid (`text_editor::table_preview`, see its own summary above — hand-rolled after all, not `markdown_blocks.rs`'s dormant mdast approach, keeping every block-level construct in this editor consistent), and a too-wide table's columns capping and cells wrapping instead of the row overflowing the pane (`table_preview::cap_column_widths`/`wrap_cell_text`, see `table_preview.rs`'s own "too wide for the pane" bullet above). Note that dotted sub-numbering like `1.1 text` isn't Markdown list syntax at all (CommonMark nests via *indentation* — e.g. `1. outer` then an indented `1. inner` — not decimal numbering), so `1.1` not getting a marker/bullet is correct per CommonMark itself. List-in-list compounding on one line (`- - x`) is still not treated as nesting — nesting is resolved only by indentation, across lines, not by a second marker following the first on the same line (see `compound_inner`'s doc comment). Lazy continuation is deliberately simplified relative to real CommonMark: a continuation line stays part of the open list/blockquote *regardless of its own indentation* (mirroring how a blockquote's lazy continuation already needs none), rather than replicating CommonMark's stricter per-list-item content-column alignment rule. A table's cells are never inline-scanned (no bold/code/etc. inside a cell — plain text only, see `push_cell_content`'s doc comment), and a table nested inside a blockquote/list isn't recognized. Deliberately deferred past all eight increments:
  - **Full CommonMark emphasis resolution** — `live_preview.rs`'s bold/italic matching is a simplified `**x**`/`*x*` pairing, not the real left/right-flanking delimiter-run algorithm; nested or adjacent-delimiter edge cases aren't guaranteed correct.
  - **Keeping formatting visible on the active line** — right now the cursor's line always renders fully raw/unstyled (no hidden markup, but also no bold/italic/heading/blockquote/list styling); a closer-to-Obsidian feel would keep the *styling* while only un-hiding the delimiter characters themselves.
  - **Heading size** — headings currently render bold-weight only, not larger text, since `shape_line` takes one `font_size` for the whole line; giving headings their own size would need a different approach (e.g. a taller line reserved for heading lines).
  - **Code/wikilink/link/blockquote/list-marker colors are flat hardcoded `Hsla` constants** in `element.rs` (`CODE_COLOR`/`WIKILINK_COLOR`/`LINK_COLOR`/`MUTED_COLOR`), same "not yet pulled from the theme" compromise as `SELECTION_HIGHLIGHT`.
- **Markdown spec gap-fill landed**: a pass checking Live Preview against CommonMark/GFM added backslash escapes, HTML entity references (common named subset + full numeric), thematic breaks (rendered as a vector rule), inline links (`[text](url)`), autolinks (bracketed and bare GFM), and GFM task-list checkboxes (render-only) — see `live_preview.rs`'s own module-doc entry above for each one's implementation. Three things that pass explicitly did **not** add, with reasoning, not silence:
  - **Images** (`![alt](url)`) — deferred entirely, not touched: this editor has no bitmap-paint pipeline (text + vector quads only), so there's nothing to render one *as* yet. A leading `!` before `[...]` suppresses the new link match for exactly this reason, leaving image syntax as untouched raw text rather than rendering its alt text as a styled (but misleading) link.
  - **Setext headings, 4-space indented code blocks, link reference definitions (`[text][ref]`/`[foo]: url`), and raw inline/block HTML** — declined **permanently**, not just parked: ATX headings/fenced code/wikilinks already cover the practical need, indented code conflicts with list-item indentation (the same ambiguity that makes most modern Markdown flavors de-emphasize it), raw HTML doesn't fit a native-rendering note app's own philosophy, and reference-style links are rare in a vault that already has wikilinks for internal linking.
  - **Hard vs. soft line breaks** — not applicable, no code change needed: every source `\n` is already rendered as its own row (this editor never joins/reflows adjacent source lines into one paragraph the way a "real" Markdown renderer does), so the CommonMark distinction — which only matters when multiple source lines *do* get joined — has nothing to attach to here.
- **True WYSIWYG table editing** — right now a table's raw `| a | b |` / `| --- |` syntax is still what you actually type and edit (just rendered as an aligned, boxed grid via `table_preview`/vector-painted borders when the cursor is elsewhere, see above); the idea for later is hiding that raw syntax from the user entirely and letting them edit a rendered cell's content directly, Obsidian/Notion-style, rather than editing pipe-delimited source text. No design work done yet — explicitly deferred, not a priority right now.
- **Obsidian-style callouts landed** (`> [!info]`, see `callout.rs`'s own module-doc entry above) — render-only, top-level-only. Two things explicitly deferred (not declined, unlike the spec gap-fill's four permanent declines above — these are real future work, just not now):
  - **Fold/collapse interactivity** — the `+`/`-` marker is parsed and hidden, but every callout always renders fully expanded regardless of it. Per the user: this (and every other render-only interactivity gap — task-checkbox toggling, WYSIWYG table editing) waits for Jade's later, dedicated "interactions" phase, not picked up piecemeal alongside rendering work.
  - **Nested callouts** — a callout inside another callout (`>> [!note]` inside `> [!info]`), or a callout as a list item's content, both fall through as plain nested/compounded blockquote content rather than their own colored box — consistent with every other one-level compounding cap in this editor (table-in-list, wikilink-in-emphasis, etc.), not a callout-specific limitation.

## Commands

Workspace-wide:
- Build: `cargo build`
- Run the app: `cargo run -p jade-app`
- Release build: `cargo build --release` (~37MB stripped binary; see the workspace `Cargo.toml`'s `[profile.release]`/`[profile.dev]` — neither profile emits/keeps debug symbols, see that file's comment for why a debug build is still large regardless: unoptimized codegen, not debug info)
- Check (fast compile check without producing a binary): `cargo check`
- Test all crates: `cargo test -- --test-threads=1`
- Test a single crate: `cargo test -p jade-core` / `cargo test -p jade-app -- --test-threads=1`
- Run a single test: `cargo test <test_name>`
- `jade-app`'s headless UI tests **require `--test-threads=1`** — see the Headless UI tests note below for why.
- Lint: `cargo clippy`
- Format: `cargo fmt`
- Benchmark: `cargo bench -p jade-core` (criterion; compares each run against the last automatically — watch for a `change:`/`Performance has regressed` line, not just the absolute time). `jade-core`'s `benches/vault_operations.rs` covers `extract_wikilinks`/`Vault::backlinks`/`Vault::search`, benchmarking a *typical* (~1500-word) and *worst-case* (~20k-word) synthetic note/vault, generated in the bench file itself (no fixture files) — extend both tiers together if you add a new benchmark, not just one. `jade-app` has no benchmarks currently (its one `benches/markdown_parsing.rs` was removed along with `markdown_blocks.rs`, see below) — `criterion` remains a `jade-app` dev-dependency regardless, available if a future benchmark needs it.
