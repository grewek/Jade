# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Vision

Jade is an Obsidian-like note-taking app, written in Rust, with these firm decisions:

- **UI framework: GPUI** (the framework built for the Zed editor) — chosen specifically for performance. No web technology (no Tauri/Electron/webview) anywhere in the app, including for the drawing canvas described below.
- **UI components: prefer `gpui-kit`** (community component library built on GPUI) over hand-rolling widgets; only build a custom component when `gpui-kit` has no equivalent.
- **Native Excalidraw-style canvas**: a planned drawing/diagramming feature equivalent to Obsidian's Excalidraw plugin, implemented natively on GPUI's own rendering primitives — not a port or embedding of Excalidraw's web (JS/SVG) implementation.
- **Storage format**: plain Markdown files on disk (Obsidian-vault-like), not a database.
- **Phasing**: core foundation (vault handling, markdown parsing, note linking/backlinks, search — the basic Obsidian feature set) must be stable before the native Excalidraw-style canvas is built. A project-management feature is planned even later, after the canvas.

**Do not add dependencies to any `Cargo.toml` without first asking the user for explicit approval** — this applies even to crates already agreed upon in principle (e.g. `gpui`, `gpui-kit`), ask again at the point of actually adding them.

## Project state

Workspace with two crates:

- `crates/core` (`jade-core`) — UI-independent library, zero external dependencies (std only).
  - `note.rs`: `Note` — one loaded Markdown file (`id` = relative path without extension, `title` = file stem, raw `content`).
  - `links.rs`: `extract_wikilinks` — hand-written parser for `[[Target]]`, `[[Target|Alias]]`, `[[Target#Heading|Alias]]`.
  - `vault.rs`: `Vault` — recursively scans a root folder for `.md` files into `notes: HashMap<id, Note>`, and every directory (even empty ones) into `folders: HashSet<id>` (ids are `/`-separated relative paths, shared convention with note ids, e.g. a note inside a folder is `"Math/Algebra"`, its parent folder is `"Math"`). `backlinks()` builds a target-id → source-ids map by resolving each note's wikilinks (match by id, else case-insensitive title); `search()` does a naive substring match over title/content.
  - `Note::save()` writes `content` back to `path`. `Vault::create_note(title, parent)` creates a new `.md` file inside `parent` (vault root if `None`), dedupes titles *within that folder* by appending " 1", " 2", ... if taken, and returns its id. `Vault::create_folder(name, parent)` creates a directory the same way (dedupes by name, not title+extension). `Vault::update_note_content(id, content)` updates a note in-memory and persists it to disk. `Vault::rename_note(id, new_title)` renames the file in place (same folder, dedupes against existing titles the same way `create_note` does) and returns the new id. `Vault::delete_note(id)` removes the file and the in-memory entry. `note::relative_id(vault_root, path)` strips the extension (for notes); `note::relative_path_id(vault_root, path)` doesn't (for folders) — both are `/`-separated regardless of platform. Folder rename/delete aren't implemented yet (deliberately deferred — creation-only for now).
  - No Markdown rendering yet (that will need a real parser crate like `pulldown-cmark`, added only after explicit approval — see below).
- `crates/app` (`jade-app`) — binary crate, depends on `jade-core` via path dependency and on `gpui-kit = "0.7"` (which re-exports `gpui-component` as `gpui_kit::component`). `main.rs`: takes an optional vault path as the first CLI arg (defaults to `./vault`), opens it via `jade_core::Vault::open`, and renders a `JadeApp` view (implements `Render`):
  - Left sidebar: "New note"/"New folder" buttons (`gpui_kit::component::button::Button`) above a recursive, collapsible folder tree (`JadeApp::render_tree_level`/`render_folder_row`/`render_note_row`) — subfolders listed before notes at each level, both sorted alphabetically; a folder row is `div().id("folder-{id}")...` (prefixed, to avoid an `ElementId` collision with a same-named note — see the backlink-panel note below for why that matters), click toggles collapse (tracked in `JadeApp::collapsed_folders: HashSet<String>`, children just aren't rendered while collapsed — no virtualization needed at this scale) and right-click opens "New note"/"New folder" scoped to that folder. Note rows are unchanged (`div().id(note_id).test_support().on_click(...)`, highlighted when selected) but now indented by depth and found anywhere in the tree via `parent_of(id)` (an id's `/`-separated directory component, shared by note and folder ids).
  - Right pane: when a note is selected, a multi-line `gpui_kit::component::input::Textarea` bound to a `TextareaState` entity, loaded with the note's content via `.default_value(...)` and sized with `.flex_1()` (not a fixed height — must fill remaining space, not just `size_full()` on an ancestor) so it fills the window. Below it, a "Backlinks (n)" panel lists notes linking to the open note (via `Vault::backlinks()`), each entry clickable to navigate; entries are keyed `"backlink-{note_id}"` (not the bare note id) to avoid an `ElementId` collision with the sidebar's own `"{note_id}"` entries, which otherwise silently breaks click dispatch for whichever element registered last.
  - Editing autosaves: `cx.subscribe` listens for `InputEvent::Change` on the `TextareaState` entity and calls `Vault::update_note_content` on every change (no debounce yet — fine for small notes, revisit if it becomes a perf issue), and also calls `cx.notify()` so e.g. the backlinks panel re-renders live while typing, not just on the next note switch.
  - `open_note` *also* flushes the outgoing note's current editor text into the vault itself, before loading the new note — GPUI dispatches `InputEvent::Change` with a delay (confirmed via the headless harness: without this, a freshly-typed `[[Link]]` is lost if you switch notes immediately after, since the autosave subscription hadn't fired yet), so switching notes can't be allowed to depend solely on that event having already landed.
  - Clicking "New note" calls `Vault::create_note("Untitled", None)` (root) then immediately opens the new note for editing; a folder's context menu does the same with `Some(folder_id)`.
  - **Rename/delete** are deliberately *not* exposed as sidebar buttons — only via right-click context menu (`gpui_kit::component::menu::ContextMenuExt::context_menu`, items built with `PopupMenuItem`) or via hotkey (`F2` = rename, `Backspace` = delete), matching Obsidian's file-list UX. Both paths call the same `JadeApp::open_rename_dialog`/`open_delete_dialog` associated functions (take the target note's id/title/an `Entity<JadeApp>` + `window`/`cx` explicitly — not `&self` — since context-menu item callbacks only ever get `(&ClickEvent, &mut Window, &mut App)`, no `Context<JadeApp>`).
    - The hotkeys are scoped to a `"NoteList"` key context (`gpui_kit::actions!(jade, [RenameNote, DeleteNote])`, bound via `cx.bind_keys([KeyBinding::new("f2", RenameNote, Some("NoteList")), ...])`), active only while the sidebar's `FocusHandle` (`JadeApp::sidebar_focus`) is focused — set by `.track_focus(&self.sidebar_focus).key_context("NoteList")` on the sidebar container, and re-focused on every note click (and on "New note"/"New folder"). This is required so `Backspace` deletes the selected note only when the list has focus, not every backspace keystroke while editing a note's text in the `Textarea`.
    - Rename and "New folder" both open a plain `Dialog` (`gpui_kit::component::dialog::Dialog` via `WindowExt::open_dialog`) with a single-line `Input`/`InputState` and a custom `DialogFooter` (a plain `Dialog` renders no default buttons — only `AlertDialog` does). **Both also set `.on_ok(...)` with the same commit logic as the footer's confirm button** — `on_ok` is what the dialog's built-in Enter-key handling actually dispatches to, independent of whatever footer buttons are rendered; without it, Enter silently does nothing and only clicking the button works. Rename's confirm calls `Vault::rename_note` and, if the renamed note was open, reloads it via `open_note` (safe because every edit already autosaves, so there's nothing unsaved to lose). Delete opens an `AlertDialog` (`WindowExt::open_alert_dialog`, `.confirm().ok_variant(ButtonVariant::Danger)`) since it's destructive — its default footer already wires `on_ok` to both the OK button and Enter, so it didn't need this fix; its default OK/Cancel buttons have the fixed ids `"ok"`/`"cancel"`.
    - Tree-row indentation uses `.ml(px(depth * N))` (margin), not `.pl(...)` (padding) — padding only insets a box's *content* and never moves the box itself, so it has zero effect on sibling rows' horizontal alignment in a vertical flex list; margin is what actually shifts a row's position. Learned by writing a test that asserted on `ElementSnapshot::bounds().origin.x` and watching it come back identical at every depth despite the (wrong) `.pl(...)` call.
    - To update a *different* entity (not the one currently mid-update via an action handler) from inside a dialog button's `on_click`/`on_ok` callback: don't reach for `Entity::update_in` (it needs a `VisualContext`, which a plain `&mut Window` does not implement here) — just capture `window: &mut Window` from the callback's own parameters and call `entity.update(cx, |state, cx| state.some_method(window, cx))`, letting the inner closure borrow the outer `window` directly. This is the same pattern `gpui_component::root::WindowState::update` uses internally.
  - **Headless UI tests** (`#[cfg(test)] mod tests` at the bottom of `main.rs`, run via `cargo test -p jade-app`): use `gpui-kit`'s built-in `test-support` feature (enabled only under `[dev-dependencies]` in `crates/app/Cargo.toml` — release/`cargo run` are unaffected) to render the real `JadeApp` in an off-screen window and drive it with real GPUI hit-testing (`gpui_kit::test::TestWindowExt::click`/`press`/`input`/`right_click` by element id) — no `ydotool`/display/compositor needed, safe to run unattended. Any interactive `div` that a test needs to `click(...)` must carry `.test_support()` (a zero-cost no-op outside test builds) in addition to `.id(...)`, or the click silently can't find it. Opening an overlay (context menu, dialog) is asynchronous even in tests — a test must call `cx.run_until_parked()` between triggering the overlay (right-click, hotkey) and interacting with it (e.g. `window.within("popup-menu").within("items").click(<index>, cx)` for a context-menu item by its 0-based position), split across separate `cx.update_window(...)` calls; doing it all inside one `update_window` closure silently finds nothing. Inside the test module, import gpui-kit items explicitly rather than `use gpui_kit::*`/`use super::*` glob — with `test-support` on, that glob also re-exports GPUI's `test` attribute macro, which shadows plain `#[test]` and makes `#[gpui_kit::test]`'s own expansion recurse infinitely.

## Commands

Workspace-wide:
- Build: `cargo build`
- Run the app: `cargo run -p jade-app`
- Release build: `cargo build --release`
- Check (fast compile check without producing a binary): `cargo check`
- Test all crates: `cargo test`
- Test a single crate: `cargo test -p jade-core` / `cargo test -p jade-app`
- Run a single test: `cargo test <test_name>`
- Lint: `cargo clippy`
- Format: `cargo fmt`
