## Performance: the Part 1 estimate

Part 1 of the viewport-rendering fix was initially guessed at "tens of ms" and actually measured at ~1.4s — only the real number is trustworthy. This is the origin of the "always measure" rule: a plan that "sounds cheap" still gets measured before being called done.

## jade-core / vault.rs

`backlinks()` used to resolve a note's wikilinks by a linear scan per link when the link was by title rather than id, making it effectively O(notes² × links) on vaults where most links resolve by title. Fixed by building a `title_index()` once per call instead of per-link (see `benches/vault_operations.rs`, and the `fix(core)` commit that found and fixed it). `backlinks()` matters for input latency specifically because `jade-app` recomputes it on every keystroke (the live backlinks panel re-reads it on every `InputEvent::Change`), not just when switching notes.

The wikilinks cache (a private `wikilinks: HashMap<id, Vec<WikiLink>>`, kept in sync incrementally at every mutation point — `create_note`/`update_note_content`/`rename_note`/`delete_note`/`rename_folder`/`delete_folder`, moving the cached value to a new key on rename rather than re-parsing unchanged content) cut the remaining cost by ~2.7x on its own (see `benches/vault_operations.rs`). `Vault::empty(root)` exists because the cache field being private means external crates can no longer construct a `Vault` via struct-literal syntax — `jade-app`'s fallback when `Vault::open` fails needed another way in.

Even with both fixes, `backlinks()` is still O(total links in the vault) per call, since every call rebuilds the whole target→sources map from scratch. A further step would be maintaining that map incrementally (diff a note's old vs. new links on edit; also needs to account for `resolve()`'s targets shifting when *other* notes are renamed). Not done because even the worst-case measured cost (16.9ms on a 200-note × 20k-word synthetic vault) is already comfortably under the ~100ms human-perceptible-lag threshold — real complexity for a return past the point of mattering, for now.

`Vault::rename_folder` rebuilds the moved subtree's in-memory `notes`/`folders` entries by dropping anything under the old id prefix and re-running `collect_entries` over the new path, rather than hand-rewriting id prefixes for arbitrarily-nested children — simpler and less error-prone.

Tests use `tempfile::tempdir()` for a real-but-disposable vault directory per test instead of a hand-rolled `std::env::temp_dir()` + PID/counter scheme. The returned `TempDir` guard cleans up on `Drop`, including on a mid-test panic/`assert!` failure — the old manual `std::fs::remove_dir_all(&dir)` (only reached on the success path) didn't have that property.

## jade-app / text_editor — why a custom editor at all

True Obsidian-style Live Preview (markdown markup hidden/revealed per-line based on cursor position, inside *one* continuously-editable surface, not separate rendered/editable widgets swapped in and out) isn't buildable on top of `gpui-component`'s own `Editor`/`Textarea`/`InlineToken` without forking it — and a fork means separately maintaining a divergent copy of someone else's editor indefinitely, which was explicitly rejected.

An earlier Live Preview v1 attempt built exactly the per-block-widget-swap approach (swapping `TextView`/`Textarea` per block) — it worked, but was explicitly rejected for not being "one editor." That attempt's mdast-based (`markdown::to_mdast`) block-segmentation logic lived in `markdown_blocks.rs`, which never gained a consumer across three rounds of block-level Live Preview work (lists/blockquotes/list markers, fenced code, tables — each handled by a small hand-written sequential scanner instead, for consistency with each other) and was removed, along with its benchmark and the `markdown = "1.0.0"` dependency, once tables confirmed there was no remaining plausible use.

## buffer.rs

`EditorBuffer`'s cursor movement is char-boundary-based, not grapheme-cluster-based — a deliberate simplification; `unicode-segmentation` would fix it but needs its own dependency approval. `insert`/`delete_range` use "basic" linear undo (one entry per mutating call) rather than a real editor's coalescing of a burst of typing into one step — a deliberate Phase 1 scope cut.

## live_preview.rs — implementation detail

`build_display_line` is a hand-scanned parser in the same style as `jade_core::links::extract_wikilinks`, not a reuse of it directly, since hit-testing needs byte offsets that function doesn't carry. Strikethrough only recognizes the doubled-tilde GFM form (mirroring Strong's `**`/`__` pairing) since GFM itself doesn't define single-tilde strikethrough (that's a cmark-gfm extension option GitHub doesn't enable).

`compound_inner` handles one level of compounding: a heading is checked unconditionally (a heading never itself compounds further, since it swallows the rest of the line as inline content), or whichever of blockquote/list the outer one wasn't. `- - x` leaves the second `-` as plain text — list nesting is signaled by indentation, not by repeating the marker, same as real CommonMark.

The spec-gap-fill pass's details: backslash escapes are matched in `find_construct` whenever `\` is immediately followed by `u8::is_ascii_punctuation()` — a one-shot match with no closer to search for, so `\*` is caught before the following `*` could ever register as an emphasis opener. HTML entity references: numeric `&#NNN;`/`&#xHHH;` decode any valid codepoint; named references are a common subset, not HTML5's full ~2000-entry table (deliberate v1 scope cut). Thematic breaks are resolved per-line like every other inline detector here, unlike fences/tables, rendered via `hidden_line` plus a real vector rule — the same "quad over a blank gap" technique as a table's own grid lines. Inline links: a leading `!` suppresses the match entirely, since `![alt](url)` is an image and images are explicitly deferred (no bitmap-paint pipeline exists). Autolinks: the bracketed form requires `://`/`mailto:`/`@` inside the brackets so ordinary `<div>`-style raw HTML still falls through as plain text; the bare GFM form matches a literal `http://`/`https://` prefix, lowercase scheme only (a deliberate simplification). Task checkboxes: an unordered marker's bullet and checkbox collapse into one glyph (`"- [ ] x"` → `"☐ x"`), matching Obsidian/GitHub; an ordered marker keeps its number and appends the checkbox after it, since the number still carries meaning a checkbox alone doesn't. `find_closing` became escape-aware as the shared foundation underneath all of this — a no-op for every pre-existing caller's own tests.

`classify_block_context`'s state machine: for each line it's `Plain` (nothing to override), `ListMarkerLine(depth)` (computed by popping/reusing/pushing an indentation-column stack as each successive marker line is seen — a deeper indentation opens a new level, the same column reuses the current level as a sibling item, anything shallower pops back to an ancestor), or `LazyContinuation(LineIndent)`. A blank line or heading always closes whatever was open; a fresh blockquote/list line replaces whichever was previously open outright, rather than nesting the two together.

## table_preview.rs — implementation detail

The tricky part of keeping cell text a genuine click target: a naive one-`push_replaced`-segment-per-blank-gap-and-cell makes `raw_offset_for_display` skip it entirely (since that function treats every `is_replaced()` segment as unclickable) — with every segment in a row replaced that way, a click anywhere in the row fell through to the line's end. Fixed by `push_cell_content` splitting each cell into its original (trimmed-away) whitespace plus the trimmed text itself, pushed via `push_visible` (byte-for-byte) whenever it contains no backslash; the rarer escaped-pipe case falls back to one collapsing segment, a known imprecision.

Grid lines are painted as real vector quads, not box-drawing glyphs (`┌`/`│`/`┼`/etc.) — a monospace font's glyphs don't reliably abut pixel-for-pixel across separately-shaped/painted lines or at junctions, which read as visible seams/gaps between them. An earlier version of this feature tried the glyph approach; replaced after it visibly didn't look like a clean closed box. `InlineStyle::TableBorder` was removed outright once nothing needed a distinct border-glyph color any more.

`cap_column_widths` shrinks every column's natural width proportionally to how much each column could shrink (a wide column gives up more than a narrow one), never below `MIN_COLUMN_WIDTH`, after which it's clamped flat once the budget is too tight to proportion at all.

## callout.rs — implementation detail

Telling a callout's header line apart from a body line that also starts with `>` requires knowing whether the blockquote block just opened on this line or is continuing from above — `live_preview::classify_block_context`'s own `Open::Blockquote` state never needed this, since every `>`-prefixed line is already self-sufficient for plain blockquote rendering. `callout`'s state carries a *count* (`callout_counts`) because a callout's index into `self.callouts` is only meaningful relative to how many exist before it — two states can coincidentally be equal while a different number of callouts were created to reach them.

`Callout` deliberately only carries `kind`/`start_line`/`end_line`, not the parsed header itself — unlike a table's column widths, a header is resolvable from its own single line alone.

## element.rs — the big rendering-architecture history

**Soft line-wrapping** fixed a real overflow bug: a line too wide for the pane used to be simply unreadable, clipped/overflowing past the editor's own width with no horizontal scroll either. This was a real architecture shift, not just a parameter — every place that used to assume "one raw line = exactly one `line_height`-tall row" needed to stop doing that. `paint_lines`'s selection highlight is the one genuinely more complex case: a selection spanning more than one wrapped row within the same raw line now paints one rect per affected row rather than the single rect that sufficed when every line was exactly one row.

`measure_document`'s width estimate falls back to `Pixels::MAX` (effectively "assume no wrap") when `editor.scroll_handle.bounds().size.width` is zero — before a tracked ancestor has ever been laid out for this specific `Editor`. Confirmed empirically (`main.rs`'s own `a_line_too_wide_for_the_pane_wraps_instead_of_overflowing` test) to already resolve correctly on the *first* render after opening a note in the real app, not needing a stale extra frame to catch up. A bare `Editor` with no such tracked ancestor (`text_editor::element`'s own test harness) always hits that fallback — which is why wrapping-aware *sizing* specifically, and viewport-bounded-rendering tests specifically, can only be exercised through the full `main.rs`/`JadeApp` harness.

**Viewport-bounded rendering** fixed a real, user-reported "lags like crazy" bug: opening a 320,485-line/11.3MB stress-test note took ~10.1 seconds per `render_frame`, including a second, back-to-back paint where nothing had changed at all. Root cause confirmed by direct measurement before touching any code (a now-removed headless probe), not guessed. Measured result: ~10.1s → ~1.4s on the same stress file (`main.rs`'s `opening_a_huge_file_does_not_take_several_seconds_to_render`, threshold deliberately loose — under 3s, not a tight bound) — a real ~7x win, but not yet a 60fps frame budget.

**Incremental classification caching** replaced the four classify_* passes' own "whole document, fresh every paint" cost (confirmed ~420ms combined on the stress fixture) with sub-millisecond patches. `fenwick::Fenwick` is a classic binary indexed tree over per-line byte strides, O(log n) point-update/prefix-sum. Reconverging on a merely coincidental state match before having walked at least as far as every line the edit actually replaced was a real, caught bug. A still-open callout at the reconvergence boundary needs its `end_line` restored from a pre-edit snapshot, since the walk itself never revisits the lines that would otherwise keep extending it. Every patch function walks forward from a byte cursor rather than ever materializing the document's lines into a `Vec<&str>` first — an earlier draft of `patch_block_preview` did exactly that and silently reintroduced an O(document) cost per edit; caught by the 16.66ms standing rule's "always measure," not by inspection. All four were validated against their own pre-existing whole-document function (the "oracle") via randomized property tests, which is what actually caught every bug above — none were reasoned out in advance. Measured per-edit cost on the 320K-line fixture: edit_span ~3.6µs, block_preview ~0.7µs, callouts ~55µs, block_context ~0.8µs, tables ~313µs.

**`last_autoscrolled_cursor`**: without this gate, `autoscroll_to_cursor` ran unconditionally on every repaint and snapped the view straight back to the (unchanged) cursor's line the instant a manual scroll carried it out of the viewport, making it impossible to scroll away from the cursor at all (bug: scrolling "blocks" after a few lines). It's an `Rc<Cell<_>>` rather than a plain field for the same reason `scroll_handle` itself is `Rc`-backed: `render_editor` clones it out of `&Editor` synchronously and moves the clone into the `'static` paint closure, which mutates it directly.

**Tab key handling**: `gpui_kit::init`'s global `Root` component already binds plain `"tab"` to its own focus-next action in a `"Root"` key context wrapping the whole app, and GPUI resolves a keystroke against bound actions (innermost key-context first) before running any element's raw `key_down_listeners` at all, so an `on_key_down` match arm for "tab" is simply never reached. The fix is a more specific `"TextEditor"` key context outranking "Root"'s — the same mechanism already used for `RenameNote`/`DeleteNote`'s `"NoteList"` context.

## main.rs / JadeApp — UI bug history

**The dialog/editor mouse-event bug**: clicking a `Dialog` positioned over the editor (e.g. Settings, which floats centered over where the editor normally sits) also fired the editor's own `MouseDownEvent` listener, setting `Editor::is_dragging = true` — and the matching `MouseUp` that should reset it never reached the editor's listener at all, because the dialog's own `Cancel`-action close (dispatched synchronously from within that same click) poisons GPUI's shared `propagate_event` flag for the rest of that event's bubble phase, so the editor's own later-registered `MouseUp` listener never got walked. Left stuck, every subsequent mouse move (even with no button held) kept extending a selection until the next real click on the editor. `occlude()` only gates GPUI's `Hitbox::is_hovered()`-based convenience wrappers (`.on_click`, hover, tooltips), never the raw mouse-listener dispatch loop — which is why the fix had to be an explicit `window.has_active_dialog(cx)` check rather than relying on occlusion.

**Icon assets**: found via a real bug report — "I can't see the x... if I hover over it I see the block getting gray but it seemingly has no content." Without `.with_assets(gpui_kit::assets::Assets)`, every `IconName` renders as nothing: the icon's own `Button`/container still paints (hover state and all), just with empty content where the SVG should be.

**Command palette global dispatch**: GPUI's action dispatch only walks the path from the currently focused node up to the tree's root; with nothing focused at all (e.g. right after opening the app, or right after closing a dialog — a real user-reported bug), that path collapses to a single node with no listeners on it, so an element-attached `.on_action` a level below is simply never reached, even though the `None`-context keybinding itself still matches fine. `cx.on_action`'s global listeners run unconditionally in both dispatch phases, independent of any path, sidestepping this entirely. The handler gets to a window via `cx.windows().into_iter().next()` + `cx.defer(...)` + `window_handle.update(...)` — not `cx.active_window()`, which queries genuine OS-level platform focus and is reliably `None` under the headless test platform.

**Tree-row indentation**: learned by writing a test that asserted on `ElementSnapshot::bounds().origin.x` and watching it come back identical at every depth despite a (wrong) `.pl(...)` call — padding only insets a box's content and never moves the box itself.

## Headless UI test non-determinism investigation

Confirmed via controlled A/B testing under added CPU load (12 busy-loop processes pinning all 16 cores): single-threaded (`--test-threads=1`) stayed at 0 failures across 35 runs both with and without the extra load, while the default parallel harness went from an occasional failure at idle to roughly 80% of runs having at least one failure under load — and the failures weren't confined to one test, implicating a genuine concurrency bug in the vendored `gpui`/`gpui-base`/`gpui-component`/`gpui-kit` test-support stack (likely in its thread-local element-observation registry or test executor's "parked" detection, not yet pinned down further) rather than anything in Jade's own code or the `tempfile` migration. Re-check this if a future `gpui-kit` upgrade might have fixed the underlying race — don't just re-add parallel test execution without re-verifying under load first.

A real trap found this way: an element with only `.id(...)` and no `.test_support()` is invisible to `try_find`, not just unclickable, and won't even show up in a failed lookup's "Registered paths" debug dump — the handler that's supposed to produce it can be confirmed running (e.g. via a temporary `eprintln!`) while the assertion right after still fails as if nothing happened.

## Debug build slowness investigation

Investigated after a user report of "huge delay" opening `vault/Markdown Showcase.md` (235 lines, every construct including all 13 callout types). Directly measured the actual markdown-rendering pipeline in a headless test and found it fast regardless — a full `render_frame` of that whole file took ~8ms, and every new callout icon glyph (including exotic ones like `☰`/`☠`/`☷` that could plausibly trigger slow font-fallback resolution) shaped in 8–20 microseconds each, even cold. That ruled out an algorithmic bug in `classify_tables`/`classify_callouts`/`classify_block_context`/`build_display_line` or friends — confirmed by having the user try the exact same file against a `--release` build, where the delay disappeared entirely. A headless test can't measure real GPU compositing at all (it likely doesn't even hit a real GPU surface), so this class of slowdown is invisible to that harness by construction.

## Row-height caching (`RowHeightCache`) measurement journey

Landed by directly porting the exact shape `DocumentCache`'s own incremental-classification work already established, rather than designing something new: a `Fenwick` tree over per-line values (row counts instead of byte strides), a touched-line range returned from the edit path, and a randomized property test against a full-rebuild oracle (which is what actually validated the result here too, not just `cargo test` passing by luck).

One real design choice made along the way: whether to patch `RowHeightCache` *at edit time* (inside `Editor::record_edit`/`invalidate_all`, needing `Font`/`available_width` computed outside of a paint for the first time anywhere in this codebase) or *lazily at the next render* (deferring to `analyze_line_layout`, which already has those values). Edit-time won, for one case specifically: a pure cursor move with no edit (arrow keys, a mouse click) isn't reported through `record_edit` at all — hooking that into every one of the many cursor-moving call sites in `editor.rs`/mouse handling was rejected as needlessly invasive, in favor of a cheap lazy check inside `analyze_line_layout` itself (`sync_active_line`, comparing the current active line against what was last cached — same shape `last_autoscrolled_cursor` already uses to catch "the cursor moved" without being wired into every mover). The edit-triggered path still patches synchronously in `record_edit`, since by the time the next render happens there'd be no way to recover *which* lines an edit touched without re-deriving it — `DocumentCache::record_edit`'s own touched-range return value only exists for the duration of that call.

`render_params` (in `element.rs`) is the one new piece of shared plumbing this needed: the exact font/font-size/text-color/available-width computation `render_editor` already did inline, now also called from `Editor::record_edit`/`invalidate_all` so the row-height patch at edit time uses the identical values the next render would. `Window::text_style()`/`window.line_height()` turned out to already be safely callable outside of a paint closure — confirmed by `input_handler.rs`'s pre-existing `bounds_for_range` already doing exactly that for IME positioning, not something newly discovered here.

**Measured result**: `main.rs`'s `typing_in_a_huge_file_after_it_is_open_is_fast` (release build, 320K-line stress fixture) went from the Backlog's own ~140-155ms figure to `edit=~15-20ms render=~13-16ms`. The render half is the one this cache actually targets, and it landed close to the 16.66ms/60fps bar (confirmed via temporary instrumentation inside `analyze_line_layout`/`RowHeightCache` itself that it's correctly taking the cheap `sync_active_line`/`patch_lines` paths, not silently falling back to a full `rebuild` every time — `rebuilt=false touched=Some(0..1)` for a typical single-character edit deep in the fixture).

The edit half (~15-20ms) turned out to be *mostly outside this codebase's own code* — confirmed by the same temporary-instrumentation discipline, not guessed: `Editor::record_edit`'s own work (classification patch + row-height patch combined) measured ~1ms; `EntityInputHandler::replace_text_in_range`'s own buffer mutation (`EditorBuffer::insert`, a `String` byte-shift) measured ~1.5-2.5ms; the remaining ~15ms is spent somewhere inside GPUI's own `dispatch_keystroke` path before `replace_text_in_range` is even entered, in the vendored gpui/gpui-base/gpui-component stack rather than Jade's — not pinned down further (would need digging into vendored code), flagged in the Backlog rather than silently dropped. One small, genuinely in-scope fix did fall out of this same measurement pass: both `replace_text_in_range` and `replace_and_mark_text_in_range` were unconditionally cloning the entire buffer (`buffer.text().to_string()`, confirmed ~1ms on this fixture) before checking whether `range_utf16` was even `Some` — it's `None` for every plain keystroke dispatched this way, not just real IME composition, so the clone was wasted almost all the time. Fixed by `resolve_replace_range`, which only borrows `buffer.text()` (no clone at all, in either branch) when `range_utf16` is actually `Some`.

## Memory-usage investigation and `test_alloc.rs`'s own bug

A real user report (2026-11-14, right after `RowHeightCache` landed): ~189MB RSS at startup, ~3xxMB with the 320K-line stress fixture open, no edits made — "that's a tad too much." First pass was pure reasoning from the actual struct definitions (no profiling): text (~11.3MB) + `DocumentCache`'s eight parallel per-line arrays (several `Option<usize>` fields at 16 bytes each, no niche optimization) + `RowHeightCache`'s `Fenwick` came to a rough ~45MB estimate — nowhere near the observed 100-200MB delta, which is what justified building real measurement tooling rather than continuing to guess.

`test_alloc.rs`'s counting `GlobalAlloc` wrapper was the result — and building it caught a real, severe bug in itself before it caught anything in the rest of the codebase: its first version's `reset()` zeroed `CURRENT_BYTES` unconditionally. The *first* time this ran (in isolation, one test at a time), that's harmless — nothing was live yet. But `cargo test`'s full suite runs every test in one long-lived process; by the time a *later* test's `reset()` call fired, there was real, already-live memory from earlier tests (an open note's buffer, caches, etc.) that `reset()` blew away from the counter's perspective without it actually being freed. When that real memory eventually *did* get freed, `dealloc`'s `fetch_sub` ran against a counter that no longer agreed with reality, underflowing a `usize` (wrapping to near its max) — and the next `alloc` afterward overflowed on add, panicking in debug builds ("attempt to add with overflow") and, before that specific panic was pinned down, manifesting first as a glibc `munmap_chunk(): invalid pointer` abort in a completely unrelated later test (`typing_in_a_huge_file_after_it_is_open_is_fast`), the classic signature of heap-metadata corruption from a mismatched alloc/dealloc accounting bug — not a bug in whatever test happened to be unlucky enough to trip over it. Confirmed root cause (not guessed) by running the crashing test in isolation first (passed cleanly) to establish it was cross-test state corruption, then inspecting `reset()` specifically. Fixed by never touching `CURRENT_BYTES` in `reset()` (it must stay a true running total matched exactly to every `alloc`/`dealloc` pair since process start) and rebasing `PEAK_BYTES` to the *current* live value instead of `0` — plus, as defense in depth against any *other* still-unknown accounting mismatch (e.g. a native/FFI dependency allocating outside Rust's `GlobalAlloc` and later freeing through it), switched the counters to saturating arithmetic via a compare-exchange loop, so even an imperfect pairing degrades to a slightly-off number instead of crashing the suite again.

**What the (now-trustworthy) numbers actually showed**, opening the stress fixture once in an already-warmed-up app: ~103.5MB retained, across ~4 million allocations. Reconciling against the three measured/known pieces (text ~11.3MB, `DocumentCache` ~41.5MB — measured directly, not the earlier ~45MB guess — `RowHeightCache` ~2.6MB) left ~48MB *still* unaccounted for, which is what led to looking at `register_mouse_handling` specifically: `render_editor` clones the buffer text once for its own `paint_lines` use, clones it again (plus six `DocumentCache` per-line `Vec`s) to pass into `register_mouse_handling`, which clones the text a *third* time for `MouseDownEvent`'s closure while moving the second copy into `MouseMoveEvent`'s — and since `window.on_mouse_event` registrations from the *last* paint stay alive until the *next* paint replaces them, two full extra copies of everything sit resident even at rest between paints. Estimating that duplication's size by hand (~47MB) landed within roughly 1MB of the actual unaccounted-for gap — close enough to treat as confirmed without needing to instrument `register_mouse_handling` directly too. A separate test (`opening_and_repainting_a_huge_file_does_not_leak_per_paint_clones`) specifically ruled out this being a *leak*: `current` bytes stayed bit-for-bit identical across 10 additional unchanged repaints (`103530698` before and after), only `peak`/`count` grew — confirming it's wasteful standing duplication, not unbounded growth.

The other concrete number: `live_preview::classify_block_context_from`'s nested-list tracking (`OpenBlock::List(Vec<usize>)`, cloning the whole depth-stack via `open = next.clone()` on *every* line inside an open list, not just where depth changes) accounts for ~18MB and 98,642 of `DocumentCache`'s ~338,178 total allocations — on this fixture, 21.9% of all 320,486 lines are inside an open list, each contributing its own never-shared `Vec<usize>` allocation.

## Fixing the four findings: planning session and arena-allocator detour

Before touching any code, the user asked to plan the fix for all four items (undo stack, the two measured memory findings, plus a fifth question that came up about why opening a file allocates ~4 million objects) as one small-steps plan, and specifically asked whether arena allocators (`bumpalo`/`typed-arena`) would help more than `Rc`-based sharing.

The answer, worked through in discussion rather than by trying both: arenas change *where* memory is allocated, not *whether* data gets duplicated. Both the `register_mouse_handling` and `OpenBlock::List` findings are duplicate-*ownership* problems — the fix is to stop cloning in the first place (`Rc`-based sharing, already the dominant pattern in this codebase via `DocumentCache`/`RowHeightCache`/`ScrollHandle`), not to make the clones cheaper to allocate. There's also a practical blocker: `bumpalo`-style arenas hand back references tied to the arena's own lifetime, which doesn't fit GPUI's `'static`-closure requirement for `window.on_mouse_event` without wrapping the arena in an `Rc` anyway — at which point `Rc` is doing the actual work and the arena adds nothing. Arenas *would* fit a different, separately-identified cost well (the ~4 million transient allocations from `RowHeightCache::rebuild` calling `build_display_lines` for every line on cold-open, a "bulk allocate many short-lived objects together" pattern) — but the plan's step 4 (viewport-bounded cold-open seeding, not yet implemented as of this entry) fixes that by *avoiding* the allocations rather than by making them cheaper, so arenas weren't adopted there either. Also discussed and deliberately scoped *out* of the plan: replacing `EditorBuffer`'s `String` with a rope (`ropey` or hand-rolled) — the "architecturally correct" fix for cheap structurally-shared undo snapshots, directly relevant to the undo-stack item, but a much bigger lift and a dependency decision, left for a future session rather than folded into this one.

## Undo-stack coalescing + cap: implementation

Landed via a `last_edit: Option<LastEdit>` field tracking the most recent edit's direction (`Insert`/`DeleteBackward`/`DeleteForward` — kept as three separate kinds, not one generic `Delete`, specifically so a backspace-burst and a forward-delete-burst that happen to meet at the same buffer position don't silently coalesce into one undo step; checked this explicitly with a dedicated test, `backspacing_then_forward_deleting_at_the_same_point_does_not_coalesce`) and the buffer position a *following* same-kind edit must start at to count as a continuation of the same burst. `push_undo` simply skips pushing a new `Snapshot` when the incoming edit continues the previous one — the existing top-of-stack entry already represents "before this whole burst."

One subtlety caught by writing the tests, not reasoned out in advance: two of the *existing* tests (`multiple_undos_walk_back_through_history_in_order`, `a_new_edit_after_an_undo_clears_the_redo_stack`) did several plain inserts in a row with no break between them, which is now — correctly — exactly the case that coalesces into one entry, breaking their original assertions about multiple distinct undo steps. Fixed by inserting a harmless `buf.set_cursor(buf.cursor(), false)` between them (a cursor "move" to wherever it already is, which still unconditionally breaks a burst) rather than changing what each test was actually trying to verify.

An explicit cursor move, `select_all`, undo/redo, or an edit that replaced an active selection, all reset `last_edit` to `None` — the last three because they represent a deliberate, distinct action that shouldn't silently merge with whatever comes next, the first because moving away (even back to the same spot) is a real break in the editing session a human would expect to land on its own undo boundary.

## `register_mouse_handling` Rc bundling: the estimate was for two copies, the fix removes one

The Backlog's own estimate for this finding (~47MB) was built by hand before implementing anything, reasoning about how many *separate* clones existed at rest between paints: one made explicitly inside `register_mouse_handling` for `MouseDownEvent`'s own closure capture, and one more — the original value `render_editor` had already cloned once to pass into `register_mouse_handling` as an owned parameter — that never got re-cloned again and was simply moved into `MouseMoveEvent`'s closure instead. Two distinct copies, each the full text + six `DocumentCache` `Vec`s.

Wrapping that bundle in one `Rc` and having both closures `Rc::clone()` it doesn't reduce that to *zero* copies, though — it reduces it to *one*. Both mouse closures still need to reference something, and that something still has to persist between paints (since a `window.on_mouse_event` registration from the last paint stays alive until the next paint replaces it) — the fix is that both now point at the *same* allocation instead of each getting their own. That one remaining copy also isn't a leftover inefficiency worth chasing further: it has to be a frozen snapshot of exactly what was painted, not a live read through the `Entity<Editor>` handle those closures already carry, because `offset_for_position`'s hit-testing needs to agree with what's actually on screen — reading live state instead would risk a click resolving against content that had already changed since the last paint (e.g. mid-drag, if an edit somehow landed in between).

**Measured** (`opening_and_repainting_a_huge_file_does_not_leak_per_paint_clones`, release build): retained memory for opening the stress fixture dropped from ~103.5MB to ~79.8MB — a real ~23.7MB cut, almost exactly half the original ~47MB estimate, confirming the "two copies down to one" accounting rather than the "two copies down to zero" read a less careful estimate might have implied. Transient peak during the operation dropped by more, ~66MB (~174.7MB → ~108.7MB), since the fix also removes the *third* clone that used to happen as a one-time cost inside `register_mouse_handling` itself, not just the resting duplication. `current` staying bit-identical across 10 further unchanged repaints (unchanged from before this fix) continues to confirm this was never a leak, just wasteful standing duplication — now cut in half.

## `OpenBlock::List`: the persistent-stack ceiling was optimistic

The planning session's own analysis (see above) predicted replacing `Vec<usize>` with an `Rc`-linked persistent stack would cut this finding's allocation count from "once per line inside a list" down to "once per actual nesting-depth transition" — reasoning that most list lines are same-depth siblings, which the new structure makes genuinely free (an `Rc::clone()`, no allocation).

Measured after implementing it: allocations for `classify_block_context_from` alone dropped from 98,642 to 28,570 — a real 71% cut, and peak bytes from ~18.08MB to ~13.72MB — but nowhere near the "a few hundred/thousand, bounded by nesting transitions alone" ceiling the planning session's reasoning implied. The likely explanation, not separately re-measured to confirm: `ListNode::resume_or_push` still allocates on the very *first* marker line of any list (there's no previous level to reuse an `Rc` from, so `current` is `None` and the `other => Rc::new(...)` branch always fires) — if this fixture's list content is mostly many separate short lists scattered through the "many typical chapters" generation (plausible, not confirmed) rather than one long run of same-depth siblings, that alone would explain a much higher allocation count than the "only depth transitions cost anything" framing suggested. Reported as measured, not adjusted to match the earlier prediction — the real number is what matters, and a smaller-than-hoped-for win is still a real 71% cut, not a wash.
